## Findings (ordered by severity)

### BUG-C1 · P1 · `src/assistant/reach/egress.py:106-114` · robots.txt 3xx is treated as "no rules" and the fetch proceeds

- **Failure mode:** `RobotsCache.check()` special-cases 401/407, 403 and
  `>=500`; a 3xx response falls through to `rp = RobotFileParser()`,
  `rp.parse(resp.text)`. `follow_redirects=False` means the body of a 301
  is normally empty, so `can_fetch()` returns `True` and the target URL is
  fetched. A site that 301s `/robots.txt` to a canonical file containing
  `Disallow:` is fetched in violation of its robots policy, while the journal
  records `terminal=OK` and `untrusted_input.load` — a fail-open, not a
  `ROBOTS_UNREACHABLE` terminal. Existing tests cover 200/disallow and 503
  only (`tests/test_reach_terminal_outcomes.py:52`).
- **Evidence (local `httpx.MockTransport`, no network):** robots handler returns
  `301 Location: /canonical-robots.txt`; the canonical handler returns
  `User-agent: * / Disallow: /secret`; target handler returns 200 text.
  Observed: `ROBOTS CHECK: allowed (no exception)`;
  `FETCH ok= True terminal= TerminalOutcome.OK`; journal actions
  `reach.request → ok → untrusted_input.load → seen`. With the same
  disallow text served directly at `/robots.txt`, the existing test gets
  `ROBOTS_DISALLOWED` — so only the 3xx changes the verdict.
- **Suggested owner:** `REACH` (egress/robots path).

### BUG-C2 · P1 · `src/assistant/alive_sync.py:378,427/448/453/456` + `src/alive/envelope.py:109-120` · signed envelopes are deduped by filename, so a renamed copy replays an instruction

- **Failure mode:** ingest's idempotency ledger keys on the immutable file
  `name`, never on the envelope's `id`/`seq` or body hash. The format binds
  only the *hash suffix* of the name to the bytes (`check_name_hash`); the
  timestamp/seq prefix and the body's MAC are unchanged by renaming. Anyone
  with write access to the sync folder can copy an existing signed envelope
  to a new valid name (no `mac_key` needed), and the laptop treats the copy
  as a new message. Replaying an `instruction` yields another
  `cloud_queue.enqueue_external(…)` job in `awaiting_approval` for the same
  `wamid`; proposal/stranger envelopes can be duplicated for owner spam.
  The design's wamid dedup lives on the host (`src/alive/store.py:171`), not
  in the laptop ingest path, and `RPT-E-alive-layer` only considers a replay
  *after 7 days* (expired on arrival) — in-window copies are not covered.
- **Evidence (local fixture, no network):** create one
  `make_envelope(kind="instruction", id="wamid.replay", …)`; put bytes under
  `envelope_name(NOW, 1, data)`, ingest, then put the **same bytes** under
  `envelope_name(NOW+1min, 2, data)` and ingest again. Observed:
  `first ingest queued ids: ['wamid.replay']`,
  `replay ingest queued ids: ['wamid.replay']`,
  `awaiting_approval jobs: 2`, `name hashes valid: True`. Two owner-approval
  cards now exist for one owner turn.
- **Suggested owner:** `E` (alive-sync ingest ledger; envelope format is
  shared with `src/alive/`).

### BUG-C3 · P1 · `src/alive/webhook.py:353-382` vs `:395-400` · monthly service-message cap counts only stranger turns, not owner acks/replies

- **Failure mode:** `increment_month("service_messages")` exists only in the
  T1/T2 concierge branch. The T0 branch sends a free-form ack/rejection via
  `_safe_service_reply` for every one of up to `owner_messages_per_day=200`
  owner turns, but only increments the daily `envelopes` counter. The
  heartbeat reports `service_messages_month` from that one counter
  (`src/alive/heartbeat.py:34`) and `provision.doctor` checks only that
  `stranger_messages_per_month <= 1000` (`src/alive/provision.py:92-95`).
  So the runbook's "800 keeps total well under 1,000 free replies/month"
  invariant (`reports/RPT-E-whatsapp-runbook-20261126T083500Z.md`, §0/§1) is
  not enforced: 200 owner acks/day can be sent with the reported monthly
  figure still at 0, and no monthly refusal or warning ever fires.
- **Evidence (local fixture transport, five signed webhook POSTs from the
  single owner number, one distinct wamid each, NOW fixed):**
  `free-form service replies sent: 5`,
  `count_month(service_messages): 0`,
  `count_today(envelopes): 5`, all HTTP 200. Extrapolated ceiling with the
  shipped cap is 200/day × 30 = 6,000 free-form replies in a month with the
  reported count still 0. No existing test asserts owner replies against the
  monthly counter.
- **Suggested owner:** `E` (alive webhook/heartbeat/provision).

### BUG-C4 · P1 · `src/assistant/backup.py:144-149,204-224` · `flipped → trashed` trim never re-checks the recorded hash, so a vanished remote copy is trimmed anyway

- **Failure mode:** `plan_reconcile()` hash-verifies local bytes and calls
  `verify_remote` for `uploaded → flipped`, but the very next state
  (`flipped → trashed`) plans the trim unconditionally with reason
  "flip is durable … safe to re-run". No fresh hash/remote proof is
  requested there. If the remote copy was lost, corrupted or replaced after
  the durable flip, `reconcile()` calls `trim_mover` and moves the only
  remaining good local copy into trash while advancing the manifest to
  `trashed`. `reconcile_all()` is documented as the startup entry point
  (`src/assistant/backup.py:310-335`) and passes `trim_mover` through;
  `backup_cli._run()` happens to add its own `_hash_confirmed` check before
  step 1 (`src/assistant/backup_cli.py:597`), so the CLI path is currently
  shielded — the module-level safety contract is not.
- **Evidence (synthetic fixture, no restic/rclone/MEGA):** manifest record
  `flipped` with `sha256=deadbeef`; `verify_remote` returns
  `Verification('rclone:mega-elaria', False, 'hash', 'remote copy hash mismatch / gone')`.
  Observed: `planned actions: [('flipped','trashed','flip is durable; trim was interrupted and is safe to re-run')]`,
  `problems: []`; after `reconcile(trim_mover=…)`:
  `local file still present: False`, `manifest state now: trashed`.
  The manifest now claims two copies while the verifier proved there was
  only one. No existing test exercises a negative verifier on a `flipped`
  record.
- **Suggested owner:** `T` (`src/assistant/backup.py`).

### BUG-C5 · P2 · `src/assistant/alive_sync.py:560-565` · a future-dated heartbeat is reported as "awake" forever

- **Failure mode:** `line_status()` computes `age = (now - ts).total_seconds()`
  and only calls the line asleep when `age > max_age_seconds`. A heartbeat
  whose signed `ts` is in the future yields a negative age, so the check can
  never fire: the laptop reports `awake=True` for an arbitrarily old future
  file. There is no lower-bound/`0 <= age` guard, even though
  `alive.store.record_inbound_window()` explicitly rejects future-skewed
  timestamps in the sibling path, and the heartbeat itself carries
  `clock_suspect`/`platform_blocked` flags that deserve honest reporting.
- **Evidence (fixture backend, fixed clock):** write `heartbeat/alive.json`
  signed with `ts = NOW + 30 days`, `platform_blocked=True`,
  `clock_suspect=True`; call `line_status(..., now=NOW, max_age_seconds=2700)`.
  Observed: `{'awake': True, 'reason': None, 'asleep_since': None,
  'platform_blocked': True, 'clock_suspect': True}`. The existing test
  (`tests/test_e_alive_sync.py:288`) only checks absent/current/+2h
  heartbeats.
- **Suggested owner:** `E` (alive-sync read-only line-status view).

### BUG-C6 · P2 · `src/alive/mirror.py:112-126` + `src/alive/concierge.py:263-277` · free/busy answer counts commitments due in the past

- **Failure mode:** `busy_days()` applies only an upper horizon
  (`due > horizon: continue`). Already-elapsed due dates are counted in the
  weekday bucket, so the S-0 concierge tells a T1/T2 sender that a future
  weekday "looks tight" (or "looks possible") based on commitments that were
  due weeks ago. The docstring says "within the horizon", and the mirror is
  a snapshot of stated commitments plus a separate staleness gate — there
  is no rule that past items should still shape a future day's answer. It
  also leaks a coarse count of past commitments into a stranger-facing
  reply.
- **Evidence (fixed clock 2026-11-26 12:00Z = Thursday):** two mirror items
  with `due = 2026-11-19T12:00:00Z` (a week in the past). Observed
  `busy_days → {3: 2}`; `S0Concierge.handle(text="are you free Thursday?",
  tier="T2", freebusy_level=1, busy_days=counts).reply` →
  `"That day looks tight; she'll confirm. A different day might work better."`
  With no future Thursday commitments the correct L1 answer is
  "That day looks possible …". No existing test covers a past `due`.
- **Suggested owner:** `E` (alive mirror/concierge).

## SUSPECTS (static-analysis only — not asserted as bugs)

- **S-C1 — `src/alive/webhook.py:523-531` (`verify_hub`):** an unprovisioned
  `verify_token` is replaced by the sentinel `"\x00"`, so a GET with
  `hub.verify_token="\x00"` passes the compare. Handshake only echoes the
  challenge (no state change), but the fail-closed posture looks accidental.
  Needs an owner ruling on empty-token startup behaviour.
- **S-C2 — `src/assistant/phone_link.py:714-756` (`send_approved`):** an
  explicit `device=` argument can select a different paired device even when
  the adapter was constructed with `self.device_id`. All verb allowlists hold
  (`sms.send_sms` only); the question is whether the configured-device binding
  is an authority boundary. No in-tree caller passes `device=`.
- **S-C3 — `src/assistant/reach/egress.py:164-178,206-216`:** `resolve_and_pin()`
  validates IPs but httpx re-resolves the host at connect time; DNS rebinding
  between validation and socket open is not demonstrable with a mocked
  transport. If it must be closed, pinning belongs at the transport layer,
  not in a resolver callback.
- **S-C4 — `src/assistant/alive_sync.py:462-481`:** the receipt lists ids for
  queued instructions, proposals, expired and quarantined envelopes but not
  for `stranger_turn`/`unsupported`. Nothing prunes against receipts today
  (`src/alive/sync.py:204`), so this is currently a bookkeeping gap only.
- **S-C5 — `src/assistant/backup.py:225-232`:** a `TRASHED` record whose detail
  lacks `trashed_as` makes purge target the original HOT path. The shipped
  `AudioMovers.purge()` refuses non-trash paths, but a caller wiring the raw
  `TrashMover.purge()` would delete a newly created same-name file. No
  in-tree caller does that (`backup_cli.build_context` sets `purge_mover=None`).
