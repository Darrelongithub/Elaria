## 1. Failure being fixed (owner errand #4, 2026-11-27)

`assist errand start --root ~/Downloads "Tell me what's there, and group it
by what it seems to be for"` ended `budget_exhausted` at 12/12 having read
2 of 32 selected files, never presented a grouping, and `memory.infer`
auto-stored 13 snippet "facts" (mostly mislabelled `kind=preference`, e.g.
"Initialize Git is git init") from a survey the owner never asked to be
remembered. Survival ≠ delivery.

Three root causes in `src/assistant/errand.py`:

1. **Plan starvation.** The adaptive planner queued up to 7 candidates at
   1 step each but structured candidates fan out (inspect → read, plus
   continuation windows), so the 12-step budget burned on depth before the
   tail could run. The report step was only appended *after*
   `content.analyze` completed — an errand that died early ended without
   its report step by construction.
2. **No deliverable.** `_build_report`'s summary counted steps/files and
   never stated a grouping; the CLI printed only that accounting.
3. **Memory seeding.** `content.analyze` unconditionally queued
   `memory.infer` whenever candidates existed, and `skill_memory_infer`
   coerced any missing/unknown `kind` **to `"preference"`** — content
   snippets became owner preferences by default.

## 2. What changed

### Breadth before depth (new `fs.survey` skill, read-only allowlist +1)

* `is_survey_instruction()` gates: read-only observation asks ("tell me
  what's there", "look through X", "group …") are surveys **unless** the
  instruction explicitly asks for inference ("infer…", "remember…",
  "preferences/habits") — so the existing inference workflows
  ("Go through my workspace… infer recurring practices…") keep seeding
  probationary memory exactly as before.
* Survey plan: `fs.locate → fs.survey → [digest-deduped depth reads] →
  content.analyze → errand.report`. The analyze+report tail is appended at
  **plan time**, and the depth plan is computed against
  `capacity = max_steps − step_no − 2` with per-candidate worst-case cost
  (structured inspect+read = 2 steps). At analyze time, `memory.infer` /
  `owner.ask` are inserted *before* the already-queued report and only if
  the remaining capacity still leaves a slot for it — a run can only end
  without its report step under a hostile budget (< 3 steps), never on a
  normal folder.
* `skill_fs_survey` covers **every** selected candidate in ONE step with
  the same `streamread.inspect` skeleton every other inspection uses:
  name, format, size, content digest (+ scope), never_send — one source of
  truth for digests, no duplicated hashing folklore. Per-target failures
  are named, counted, non-fatal (FIX-HW5 spirit).
* Depth planning (`_plan_survey_depth`) then, in order: skips survey
  errors loudly; skips metadata-only formats (PDF) as *"covered by
  inspection metadata"* so they cannot crowd out readable files; collapses
  digest duplicates (loose file plans before its zip twin → **one read**);
  greedily fills the remaining capacity. Everything not read is listed in
  `report.coverage.skipped` with a reason.

### The report answers the question

`report["groups"]` (also rendered above the accounting in plain
`assist errand status`):

```json
{"label": "PDF documents", "member_count": 4,
 "representative_names": ["a.pdf", "b.pdf", "..."],
 "members": ["..."],
 "basis": {"kind": "deterministic",
           "evidence": "file extension -> format family (deterministic)"}}
```

* Axis from the instruction (`group by folder|type|purpose…`); for the
  owner's "what it seems to be for" the basis string states plainly that
  this is a deterministic structural proxy — purpose labels are never
  silently invented.
* Ambiguous axis ("group everything", "sort by date") ⇒ exactly **ONE**
  `owner.ask` through the existing pending-question seam (options:
  format/folder/purpose); the answer drives `report.grouping.axis_source =
  "owner_answer"` and the grouping itself. The axis question carries no
  `attribute`, so resolving it writes no memory.
* `report.coverage` states fractions and skips:
  `{selected: 9, metadata_covered: 9, metadata_fraction: 1.0,
  content_read: 6, content_fraction: 0.667, duplicates_collapsed: 1,
  skipped: [{target, reason}…]}`; the summary line carries the same
  fractions ("grouped 9 file(s) into 2 group(s); metadata 9/9 (100%),
  content 6/9 (67%) covered; 11 step(s), …" — answer first, accounting
  below).

### Surveys don't seed memory

* Survey ⇒ `memory.infer` is never queued. Candidates land in
  `report["unconfirmed_candidates"]`, each marked
  `status: "unconfirmed_candidate"` with a note pointing at the existing
  question/answer seam for promotion. Zero rows hit `memories`.
* Kind classification: `_deterministic_analyze` now labels its
  key/value-restatement candidates `kind="observation"`;
  `skill_memory_infer` maps missing/unknown/content-alias kinds to
  `"observation"` and **never** to `"preference"` (owner-stance kinds —
  profile/preference/commitment/relationship — still pass through, and the
  analysis prompt now states the kind rule). `assist memory` prints
  `[observation/inferred, …]` for content snippets.

## 3. Dispatch requirement → implementation map

| Requirement | Where |
|---|---|
| Breadth (names/formats/sizes/digests) before depth | `fs.survey` + `_plan_survey_depth` |
| Digest dedupe: zip member + loose twin = one read | `_plan_survey_depth` (`seen_digests`, loose-first order) |
| PDF counts as covered-by-inspection, no crowd-out | `_plan_survey_depth` skip + sweep coverage |
| Reserve guarantees `content.analyze` + `errand.report` | tail queued at locate; extras inserted before report with capacity check |
| Honest partial coverage (fraction + skips) | `report.coverage` + summary prefix + CLI |
| Groups: label / count / representative names / basis | `build_report_groups` → `report["groups"]`, CLI above accounting |
| Surveys don't seed memory; candidates report-only | `is_survey_instruction` gate in analyze branch |
| Content snippet ≠ `preference` kind | `_deterministic_analyze`, `skill_memory_infer`, prompt |
| Ambiguous axis ⇒ ONE question via existing seam | `axis_question_step()` inserted at analyze |
