## Measured, not asserted

All scoring in the new tests runs the real pinned `voxceleb_ECAPA512_LM.onnx`
on real 16 kHz speech from `models/ecapa_eval_samples.npz` (enrolment from
`spk1_snt1..3`, held-out `spk1_snt4`, `spk1_snt5`, impostors `diff_example1`,
`spk2_snt1/2`). Reproduced numbers used to design the floor:

| Input | Score |
|---|---|
| `spk1_snt4[:0.6 s]` (wake length) | 0.341 |
| `spk1_snt5[:0.6 s]` (wake length) | 0.588 |
| `spk1_snt4` post-wake **1.5 s** | 0.761 |
| `spk1_snt4` post-wake **1.9 s** | 0.776 |
| `spk1_snt5` post-wake **1.9 s** | 0.828 |
| `diff_example1` post-wake 1.5 / 1.9 s | 0.087 / 0.056 |
| `spk2_snt1` 1.5 / 1.9 s | −0.014 / 0.026 |

**Why the window is scored as captured, not padded.** The design first tried
padding every command window with digital silence to 2.5 s (production always
captures 2–3 s). Measured on the same model that *lowers* the owner's own
score: `spk1_snt4` post-wake 1.9 s = 0.776 standalone, **0.667** after
zero-padding to 2.5 s. 0.776 is the number this lane is protecting, so the
scanner sees exactly the captured bytes. Consequence, stated plainly: a hit
whose following audio is shorter than 1.5 s is **not verified** — the floor is
a property of the window, not of the clock, and a `pending_window_s` of 2.0
combined with a very long spoken command can leave less than 1.5 s of tail.

## A ruling made inside this lane (flag for the owner)

The brief says a sub-1.5 s window must not score. It does not say what happens
to the utterance. This lane chose **fail closed: no listening either.** A
window too short to verify is too short to open the microphone for, and "the
hit you did not verify opens the mic" is the same authority leak in a different
order. So a sub-1.5 s command window is a silent discard like an impostor, not
an `awaiting_command` invitation. This is now pinned by
`test_short_windows_never_reach_the_scorer` and
`test_insufficient_speech_low_confidence_is_silent_not_a_knock`. Consequence:
**the minimal flow (one utterance, wake phrase inside it) now never opens
listening.** Two utterances are required — "Elaria" plus nothing, then the
command — until the next lane wires a real wake-word detector.

## What is NOT proven

* **Hardware.** No microphone, no PipeWire, no real wake-word model exists in
  this sandbox. Every claim above is about `wake_guard.py`'s decision path
  driven by the real ECAPA artefact on corpus audio. The daemon loop that
  feeds frames and performs the timed close is **not** exercised end-to-end:
  `_hotword_loop` still has no window timer, so in production the close
  happens on the next frame after the pending buffer fills — an *additional*
  frame beyond 2–3 s. That daemon-side close is the next lane's work and is
  **not proven** here.
* **Live-speaker generalisation.** The 1.5 s floor is measured on one enrolled
  speaker and two impostor clips in this repo's corpus. It is a plausible
  floor, not a calibrated population threshold.
* **Replay detection by digest** covers byte-identical replays (the BH-H15
  shape). A re-encoded or resampled replay of the same recording is not
  detected by digest and is **not proven** — it would need liveliness
  analysis, which is out of scope here.
* **`hotword.py`** stays text-only and no real wake-word detector was wired,
  per the brief.
