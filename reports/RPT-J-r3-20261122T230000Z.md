## 2. Window-close timer — implemented, but the premise is FALSE

The order said `_hotword_loop` "closes on the next frame after the buffer fills,
so production captures past 2–3 s". I measured it before changing it, with a
5 s synthetic stream and one keyword hit at 0.1 s:

```
  frames consumed: 167  = 5.01 s of audio
  window closed at: frame 87 = 2.61 s   (stage = command_window)
  scored:           80,000 bytes = exactly 2.50 s
```

The old code closed **on the filling frame**, never after it, and never captured
past the buffer. The claim was not true of this code, and I am not going to
"fix" a defect I cannot demonstrate.

What I did instead, and why it is still worth keeping:

* `window_close_s = pending.seconds` (by construction, not the raw config — the
  buffer clamps 2.0–3.0 s) and `_window_elapsed_s`, advanced by each frame's
  **audio** duration, not wall-clock, so a stalled capture cannot age a window
  shut while holding no audio.
* `window_due()` — one named predicate for "this window is over", used by both
  `feed()` close paths. It never reports true on an un-armed guard.
* Exposure in `status()`: `window_close_s`, `window_elapsed_s`.

Honest scope, asserted in the docstring and in the test: with the shipped
config the timer and `pending.full` are the **same quantity** (elapsed audio ==
buffer bytes), so this does not change behaviour today. It makes the close
explicit and testable; it does not fix a capture overrun, because there wasn't
one.

**My first version of this test failed, and I rewrote the test, not the code.**
I had asserted the timer and `full` would disagree; they cannot, for the reason
above. `test_j_window_close_is_a_named_audio_time_condition` now asserts only
what is true.

## FINDING (new, not fixed — outside J ownership)

A verified owner never opens listening in production.

`daemon.py:1547` calls `guard.feed(frame)` and **discards the return value**.
`feed()` is the only thing that calls `verify()`, and `verify()` only sets
`ATTENDING`. Nothing calls `open_listening()` — **zero call sites outside
`wake_guard.py`** (audited: `open_listening` 0, `endpoint_closed` 0,
`wake_knock_accepted` 1, at `daemon.py:1414`).

Reproduced with the daemon's exact loop body and a real `WakeGuard`, real
keyword model seam, owner scorer returning 0.92:

```
  state            : attending
  session opened   : False
  last outcome     : attending
```

Every round-J test passes because they call `guard.open_listening()` themselves.
`test_owner_command_opens_listening_on_verified_audio` asserts the guard *can*
open; nothing asserts the daemon *does*. This predates round J (present at
`221ad22` and every commit since), so it is not a regression from this lane.

Why I did not fix it: `daemon.py` is Z's cluster. A one-line
`result = guard.feed(frame)` plus an `open_listening()` call behind it is
plausibly "one-line wiring", but it opens a microphone from a background task —
that is exactly the kind of change that deserves its own lane and its own
tests, not a drive-by from a lane that does not own the file. It needs an owner
decision, and it is the largest remaining gap in the wake path.
