- Byte-count of the owner's `/tmp/raw.pcm` is **pending**. The discriminator
  (now built and shipped, see below) maps 5 s takes to:
  `~160 KB` = s16/16k at rate · `~320 KB` = s32/16k or stereo s16 ·

Source-level fact this fix is built on (pw-cat.c, PipeWire master, verified
while writing this): the raw-stdout path and the sndfile-WAV path build the
**same** EnumFormat pod and **write the same bytes** — the sndfile path does
`sf_writef_*` of the mapped buffer interpreted at the *requested* width, and
`on_param_changed` only handles DSD, so pw-record never adapts to the
format/rate the server actually negotiated. Nothing in the container, the
argv spelling, or the node name changes one byte of the payload. The only
correct-thinking fix available without new hardware is **detection and
honest journaling** — plus counting what the pipe abandons at close — and an
owner-runnable A/B that names the delivered stream from its byte-rate.

## Sandbox differential harness (this PR)

`tests/test_bug_hw1_capture_differential.py` — 17 regression tests named
`test_bug_hw1_*`, driving the REAL `assistant.capture.PipeWireCapture` and
the REAL `pw_record_pcm_stream_command` argv, with a fake `pw-record` on PATH
emitting known-format PCM (deliberately mislabelled rate/format/width/
channel variants). Measured in the sandbox (2 s takes unless noted;
`soft_limiter` run over the full take):

| Variant delivered (argv says s16/16k/mono) | bytes | peak | rms | limited | steady peak | static? |
|---|---|---|---|---|---|---|
| honest s16/16k, amp 0.5 | 64000 | 0.5000 | 0.354 | 0.00 % | 0.5000 | no |
| honest loud s16/16k, amp 0.9 | 64000 | 0.9000 | 0.636 | 53.75 % | 0.9000 | no (limiter works) |

| s32le/16k read as s16, loud in (amp 0.8) | 128000 | 0.9986 | 0.571 | 44.25 % | 0.9986 | YES |
| s16le/48k read as s16 (rate-only) | 192000 | 0.5000 | 0.354 | 0.00 % | 0.5000 | **no — chipmunk** |
| s16le stereo/16k interleaved read as mono | 128000 | 0.5000 | 0.320 | 0.00 % | 0.5000 | no — comb phase |
| s16le/16k bswapped (endianness lie) | 64000 | 1.0000 | 0.584 | 41.75 % | 1.0000 | YES, at the labelled rate |

Conclusions the table supports:

1. **Suspect (1) — delivered format/rate ≠ label — reproduces the bug exactly.**
   The `raw_peak 1.0` signature pins the mislabel to a *width/format-class*
   mismatch (f32-as-s16, s32-as-s16), not to a rate-only mismatch (chipmunk
   keeps peaks at the source amplitude and clips nothing). A bswap (s16
   delivered big-endian, read little-endian) produces the same full-scale
   noise at the *correct* byte-rate — the rate discriminator is blind to it,
   which is why the journal ships the argv + facts and why the owner's ears
   remain the oracle.
2. **Suspect (2) — stdout pipe framing / `readexactly` alignment — refuted.**
   The same honest stream delivered in 7-byte flushes reassembles
   byte-exactly; odd tails are yielded as partial reads and counted
   (`xruns += 1`), never misaligned. A byte stream cannot "drift" into
   static.
3. **Suspect (4) — processing between pipe and WavSink — refuted as cause.**
   The limiter only compresses: an honest loud take passes through with
   peaks 0.90 → 0.82 and is never distorted into residue; a full-scale
   garbage input survives to the saved WAV with peak > 0.8 (limiter can
   never repair a mislabelled stream, and never hides it — both peaks are
   journalled). The chain is faithful; it is neither the cause nor a cure.
4. **Suspect (3) — target resolution — acquitted by the owner's A/B (PR #162).**

## What changed (capture fidelity only — nothing that alters audio)

`src/assistant/capture.py`

- **`PipeWireCapture` journals the exact argv at spawn** — public `argv`
  (`["pw-record", "--target=<node>", "--rate", "16000", "--channels", "1",
  "--format", "s16", "-"]`, byte-identical to production; the pins in
  `tests/test_record_probe_take.py` still pass unchanged).
- **Delivery accounting**: `spawned_at`, `first_frame_at`, `last_frame_at`,
  `bytes_delivered` (each chunk timestamped on read). The wall window starts
  at the FIRST FRAME, not at spawn, so the ~1.5 s PipeWire/ALSA power-up
  cannot make every take look slow.
- **`stream_facts` at stream end** (finalized once): `argv`, `expected`
  (s16le/rate/mono + `bytes_per_s 32000`), `bytes`,
  `wall_seconds_since_spawn`, `first_frame_latency_ms`, `delivery` — the
  byte-rate discriminator as pure functions
  `delivery_rate_class()` / `classify_delivery_rate()` — `dropped_tail_bytes`,
  and a note stating plainly that pw-record never reports the negotiated
  format on stdout. `delivery.mismatch_suspect` is True/False with ≥1 s of
  audio and a ≥0.5 s window, else `None` ("insufficient evidence") — never a
  guess. No audio path, threshold, limiter curve or gate is touched.
- **`classify_delivery_rate` is the bugs.md byte-count discriminator, built.**
  Known classes (±5 % naming, ±10 % suspect band): 32000 as labelled ·
  64000 s32/16k or stereo s16 · 88200 s16/44.1k · 96000 s16/48k ·
  176400 f32/44.1k · 192000 f32/48k mono | s32/48k | s16/48k stereo ·
  384000 f32/48k stereo · anything else `unclassified`.
- **`aclose()` counts what the session abandoned**: after `terminate()`,
  the drain reads the pipe until EOF (bounded 0.8 s, skipped while a read is
  in flight, cancellation still kills the child — the BH-K6 contract holds)
  and adds what it finds to `dropped_tail_bytes`, patched into
  `stream_facts`. Previously those bytes vanished silently on every close —
  the honest 0-byte/fast-stop evidence the report was missing. They cannot
  be re-fed to a session that already ended; counting them is the fix that
  exists. Normal EOF closes report 0.
- `live_level_check` (`assist doctor`) now reports `argv` and
  `delivery_rate` too — `assist doctor` on the owner's box will print the
  same discriminator without any new command.

## The 0-byte secondary symptom (in scope, stated plainly)

Mechanism, proven in the sandbox: (a) pw-record's stdout to a pipe is fully
buffered (no `setvbuf` in pw-cat) — a killed take loses up to 4095 userspace
bytes; (b) bytes already in the kernel pipe were discarded by `aclose()`
without being read — now counted; (c) a stop before the first 960-byte frame
is assembled yields a 0-byte WAV — inherent to "release before the mic woke"
(first-frame latency ~1.5 s on his machine), not fixable from the capture
edge without changing session semantics, so it is journalled, not changed.
This PR does not claim the 0-byte count will drop; it claims you will finally
be able to see *why* it happened, per session.
