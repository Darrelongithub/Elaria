**F.2 — `limiter_effective` is three-valued, and today it is -1.**
`1` limited · `0` measured, nothing to limit · `-1` **not measured**. On
`ed20344` the `-1` branch is the live one: `transcribe.py` emits
`capture_stats = {session_id, node, bytes, peak_rms, frames, peak, silence_floor,
duration_s, gated_frames, stalled, no_speech}` — no limiter counters. Folding
that into `0` would print "the limiter did not fire" about audio nobody measured.
A test pins `transcribe.py`'s actual emit shape and **goes red on purpose** the
day it starts emitting counters, so the shift from "instrument missing" to a real
measurement cannot pass silently.

**F.3 — F17 is a flag, not an assertion.**
Decision 4 keeps the F17 refusal in the probe; this tree's `daemon._ptt_start`
falls back to the PipeWire default source when `mic_target` is unset. A probe
that printed `refusal f17_no_node` against code that opens the default would be a
lie with a straight face. So the probe prints which world it is describing:

* `--policy as-built` (default) → `fallback_to_default 1`, `capture_would_refuse 0`,
  `effective_node <the default source>`, `f17_refusal_implemented 0`
* `--policy f17` → `refusal f17_no_node`, `capture_would_refuse 1`,
  `effective_node -1`, `f17_refusal_implemented 1`

`f17_refusal_implemented` is never inferred — it follows the flag. If the daemon
is changed to refuse, the default flag should flip and the test that pins
`daemon.py`'s resolution order will go red first.

**F.4 — "first byte" is reported as two distinct facts.**
`first_byte_ms` is when the sample left the player; `first_byte_hex` is the wav's
**first** sample (not its peak) so a leading run of `0000` is visible as silence
at the head of the file. `wav_peak` is the loudest sample. A player that returns
in under half the audio's own duration reads `exit_zero_no_output`, because
`paplay` exits 0 after handing samples to a sink nothing is listening to. A
player that exits 0 after a plausible duration and whose first sample is non-zero
reads `played` — which is the probe's **optimistic** reading, not proof of
audibility; the `fails_to_discriminate` line says so on every run.

**F.6 — `--policy` and `--self-test` were added beyond the letter.**
The letter asks for "positive control" and "negative control" on each reader but
does not say how a reader proves it is not vacuous on a machine with no audio
stack. `player_probe.py --self-test` spawns real OS processes that impersonate a
player (good / early / complaining) plus an all-zero wav, so the controls run

letter's own invocations still work unchanged.
